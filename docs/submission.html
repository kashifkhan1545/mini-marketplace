2. Plan

What I understood

The company is building a multi-vendor marketplace, something in the spirit of Amazon or eBay, where many independent sellers list products and buyers shop across all of them. This test is a deliberately small slice of that: one product with a lot of configurable options (colour, size, storage, headboard, base, assembly), three kinds of user (buyer, seller, admin), and the same data showing up on a website and on a phone.

The hard part isn't the screens. It's that the options and their prices must live in the database, entered by the seller, so any seller can describe any product the same way and the price is always calculated the same way. If the bed's options were typed into the buyer page, I'd have built a one-product shop, not a marketplace. So I treated that as the core and built everything else around it.

Note: I worked from the test brief itself. If there's a job description or project background I should have read, I'd be glad to go through it and adjust this plan.

What I built first, and why

  1. The pricing rule and data model, before any UI. One small shared function, base price + the price of every chosen option, used by the browser for the live price and by the server at checkout. If these two ever disagreed, the whole product would be untrustworthy.
  2. The backend and database (Supabase + Next.js API): roles, products with option groups, orders.
  3. The buyer flow: browse, product page, cart, checkout. This is the one the reviewer will actually click through.
  4. Seller and admin screens, then mobile polish and the Android app.

Stack

Next.js (website and API in one project), Supabase (Postgres, login, image storage), Vercel (hosting), React Native with Expo for the Android app. I chose one backend for both web and app, so there's one set of business rules to get right. I picked tools I could move fast in and deploy for free.

Database tables

  • profiles: user, role (buyer / seller / admin), seller approval status
  • categories: Furniture › Divan Beds (only this one, as asked)
  • products, product_images: title, base and compare-at price (stored as numbers), status, gallery
  • option_groups, option_values: "Size", "Storage" and so on, each value with a label, a price change and (for colours) a swatch colour
  • orders (one per seller per checkout, with a status) and order_items (a snapshot of the title, image, price and chosen options at purchase time, so later edits never rewrite history)

What I chose to skip

Real payments (checkout is a pretend one), emails, delivery tracking, analytics, reviews, stock levels, and more than one category. The brief said to decide and say so. I'd rather have one flow that really works than many half-finished ones.

How I split the time

Roughly: first a short stretch on the data model and pricing rule; the biggest block on backend plus the buyer flow; then seller, admin and orders; then mobile-responsive polish; then the Android app and deployment; and the last stretch on testing, the README and this document. I worked in that order rather than strictly by the clock.

4. AI notes

Tool used: Claude Code (a Claude model) did most of the hands-on work with me directing it. It wrote the SQL migration, the API routes, the pages, the shared pricing code and the Android app, and it ran the Supabase, Vercel and Android build tooling. I made the product decisions (stack, what to skip, the pricing rule) and reviewed and tested what it produced.

One thing the AI got wrong that I had to fix: the first mobile product page looked fine in code and passed a check for horizontal scrolling, but on a real 360px-wide screenshot the photo gallery, title and swatches were running off the right edge. The automated "no sideways scroll" check had been fooled because the page hides overflow. The cause was a CSS grid whose children weren't allowed to shrink (min-width: 0 was missing). I only caught it by looking at an actual phone-sized screenshot, not by trusting the check. After the fix, I re-checked it the same way.

AI feature in the product: a seller can upload a product photo and get a suggested title and description (a Claude vision model). See the status note below, since it needs an API key to run.

5. Honest status

Working, and tested

I ran a scripted end-to-end test against the live site using all three accounts:

  • Logins for buyer, seller and admin work.
  • Five different option combinations were priced and ordered. All five prices matched my hand calculation exactly: £359.99, £679.98, £429.99, £639.98 and £419.99.
  • The order stored every chosen option per line (including assembly). The buyer saw the order and the seller saw it too.
  • The seller moved the order New → Confirmed → Shipped → Delivered, and the buyer saw the new status.
  • Permissions hold: a buyer trying a seller or admin action gets "forbidden" (403); the admin can reach the admin data.
  • The website was checked at 360px width (no sideways scroll on home, product, cart, login) and has a sticky Add-to-Basket bar, 44px+ tap targets, a swipe gallery with thumbnails and click-to-enlarge, search and filters (price, colour, size, category).

Built, but not fully proven

  • AI photo-to-description feature: not live. The code is there, but no API key is configured on the live site, so it currently answers "AI is not configured". I haven't seen it produce a real result.
  • Android app: built and compiled with the live site as its backend, and the screens are written (list and search, product page with options and live price, cart, checkout, orders, login). I tested the app's backend calls through the live API test above, but I have not clicked through the app on a physical phone for a long session. Treat it as a working first version.
  • PWA install on a phone: the manifest and icons are in place. I haven't personally done "Add to Home Screen" on an iPhone.
  • Seller product form and admin screens through the browser: the pages exist and the underlying API calls were tested. I did not script a full click-through of every form field in a browser. The bed itself was loaded by a seed script; the video is where the seller form is shown in use.

Not done

  • Real payments, emails, delivery tracking and analytics (skipped on purpose, as allowed).
  • The optional push notification for order-status changes. The mobile order list refreshes itself every 15 seconds instead.
  • Automated tests. All my testing was scripted checks and manual looking, not a test suite in the repo.
  • Admin and seller screens in the mobile app. Only the buyer flow is in the app, which is what the brief required.

Things I want to be upfront about

  • Default price vs the brief. The brief gives £269.99 as the base for a "small single", but also lists Small Single 2FT6 as +£90. I followed the table literally, so the page opens at £359.99 with the smallest size selected. If £269.99 should be the starting price, it's a one-line data change.
  • The plan was written alongside the build, not sent beforehand. The brief asks for the plan before coding. I didn't send it first, and I'd rather say so than pretend.
  • Row-level security is on for every table with no public policies, and all access goes through the API with server-side role checks. It's safe by default, but I haven't done a formal security review.

What I'd do with two more weeks

  1. An automated test suite for the pricing rule and the order flow, run on every push.
  2. Real payments (Stripe), order emails and push notifications for status changes.
  3. Stock levels per option combination, and a price-rule editor (e.g. bundle discounts) for sellers.
  4. Proper image handling (resizing, a CDN), a fuller seller dashboard, and many categories with category-specific option templates.
  5. A real security pass (rate limiting, input validation review, audit log for admin actions) and accessibility testing.
